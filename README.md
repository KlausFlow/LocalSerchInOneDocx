# Локальный RAG по одному документу

## Описание задачи

Скрипт `rag_query.py` позволяет задавать вопросы по содержанию одного текстового документа и получать ответы, основанные только на найденных фрагментах этого документа.

Решение сделано как простой локальный RAG-прототип: документ читается, делится на фрагменты, по вопросу находятся релевантные части текста, после чего ответ формируется только на основе найденных фрагментов.

Внешние API и облачные модели не используются.

## Что сдаётся

В решении находятся три основных файла:

- `rag_query.py` — основной скрипт;
- `requirements.txt` — список зависимостей;
- `README.md` — инструкция по запуску и описание решения.

## Минимальная функциональность

Скрипт умеет:

- запускаться из командной строки;
- принимать путь к документу через аргумент `--document`;
- принимать вопрос через аргумент `--question`;
- находить релевантные фрагменты документа;
- формировать ответ только на основе найденных фрагментов;
- выводить в консоль вопрос, итоговый ответ и 2–3 источника;
- писать, что ответа нет, если в найденных фрагментах не удалось найти подходящую информацию.

## Установка

Рекомендуется использовать виртуальное окружение.

```powershell
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
```

## Запуск

Базовый запуск:

```powershell
python rag_query.py --document ./document.txt --question "Какая цель программы?"
```

Пример с абсолютным путём:

```powershell
python rag_query.py --document "D:\\Python\\RagText\\document.txt" --question "Какие факторы описаны в документе?"
```

Пример с выводом диагностических оценок retrieval:

```powershell
python rag_query.py --document ./document.txt --question "Какая цель программы?" --debug-scores
```

Показать инструкцию, по которой формируется ответ:

```powershell
python rag_query.py --document ./document.txt --question "Какая цель программы?" --show-prompt
```

## Поддерживаемые форматы документов

Скрипт поддерживает:

- `.txt`;
- `.md`;
- `.pdf` — если в PDF есть текстовый слой;
- `.docx`.

Для сканированных PDF без текстового слоя OCR не реализован.

## Как работает решение

Пайплайн реализован явно, без высокоуровневых RAG-фреймворков:

1. Документ читается из файла.
2. Текст нормализуется.
3. Документ делится на фрагменты по предложениям с перекрытием.
4. Для фрагментов строятся локальные представления:
   - BM25 по леммам;
   - TF-IDF по словам и биграммам;
   - TF-IDF по символьным n-граммам;
   - LSA через `TruncatedSVD` поверх TF-IDF.
5. Вопрос анализируется и преобразуется в поисковое представление.
6. Скрипт ранжирует фрагменты по релевантности.
7. Из найденных фрагментов выбираются наиболее подходящие предложения или небольшие окна предложений.
8. Итоговый ответ выводится вместе с источниками.

Документ целиком в answerer не передаётся. Для ответа используются только найденные фрагменты-кандидаты.

## Почему не используется внешняя LLM

По заданию можно использовать эмбеддинг-модели, векторные индексы или собственную реализацию. В этом решении выбран локальный вариант без внешних API и без скачивания больших моделей.

Это сделано для воспроизводимости: достаточно установить зависимости из `requirements.txt`, после чего скрипт работает локально.

## Инструкция для ответа только по найденным фрагментам

Внутри скрипта явно задана инструкция:

```text
Ты отвечаешь на вопрос только по найденным фрагментам документа.
Не используй внешние знания и не добавляй факты, которых нет в контексте.
Если в найденных фрагментах нет ответа, напиши: "В найденных фрагментах нет ответа."
```

Её можно вывести командой с параметром `--show-prompt`.

Так как в решении не используется генеративная LLM, ответ формируется extractive-способом: скрипт выбирает и объединяет подходящие предложения из найденных фрагментов.

## Основные параметры

- `--document` — путь к документу.
- `--question` — вопрос по документу.
- `--chunk-size` — размер фрагмента в словах, по умолчанию `220`.
- `--overlap` — перекрытие фрагментов, по умолчанию `60`.
- `--top-k` — сколько источников вывести, по умолчанию `3`.
- `--candidate-k` — сколько найденных фрагментов передать во внутренний answerer, по умолчанию `16`.
- `--neighbor-radius` — сколько соседних фрагментов добавить вокруг найденных, по умолчанию `0`.
- `--retriever` — режим retrieval: `local`, `lexical` или `bm25`.
- `--max-answer-sentences` — максимальное число предложений в fallback-ответе, по умолчанию `3`.
- `--debug-scores` — показать компоненты оценки релевантности.
- `--show-prompt` — показать инструкцию ответа по найденным фрагментам.

## Допущения и ограничения

Это прототип, а не полноценная поисковая система и не генеративная LLM.

Основные ограничения:

- лучше всего работает, когда ответ явно присутствует в документе;
- при сильной переформулировке вопроса качество может снижаться;
- PDF должен содержать текстовый слой;
- OCR для сканов не реализован;
- ответ формируется extractive-методом, поэтому может быть менее плавным, чем ответ большой языковой модели.

Главное свойство решения: оно работает локально, прозрачно и не добавляет информацию из внешних знаний.
